# Согласованный автоматический цикл Floating IP

Политика владельца от 30 октября 2026: MTProto Checker — первый источник.
При OK лишний TCP-запрос Check-Host не выполняется. HTTPS веб-адреса остаётся
отдельной диагностикой; его ответ не доказывает работоспособность MTProto.
При RKN_BLOCK/DATA_CUT проверяется Check-Host. Отказ из двух RU ASN вместе с
валидным MTProto-отказом при рабочих данных внешней точки запускает замену.
При расхождении — уведомление владельцу; подтверждение запускает заключительную
проверку. Без ответа проверки выполняются через +15/+20/+25 минут: все три должны
подтвердить MTProto-блокировку при доступности внешней точки. UNKNOWN, одиночный
таймаут, неисправность сервиса снаружи или потеря Agent не разрешают покупку.

## Этапы и границы

- До заказа проверяются актуальность инцидента, согласование, связь и сетевой
  помощник Agent. Primary/management IP не заменяется и не удаляется.
- Заказ сохраняется до POST. Неопределённый ответ не разрешает повторный заказ.
  Операция останавливается для сверки, режим выключается и владелец уведомляется.
- История проверяется до Attach. Известный заблокированный адрес удерживается
  без назначения; следующая покупка использует другую постоянную операцию.
- Назначение Cherry выполняется через UUID primary IP, проверяется GET.
- Agent добавляет /32 через отдельный ограниченный Unix-сокет помощника.
  По умолчанию локальное разрешение отсутствует. Проверяются UID, management IP,
  адрес, UUID и собственный журнал. Нет удалённого shell, provider-ключей или
  команд изменения default route/Telemt. Новый адрес защищён rollback-таймером.
- После проверки MTProto кандидат сохраняется через свою systemd unit, таймер
  отменяется. DNS использует ранее проверенный адаптер append/remove только
  выбранной A-записи поддомена vetka.rest, с журналом и проверкой остальных записей.
- Успех требует DNS-кворума и MTProto OK по IP и домену из RU/внешней точки.
  Только противоречивый ответ проверочного сервиса повторяется один раз.
- Старый управляемый Floating IP и отбракованные кандидаты освобождаются после
  успешного перехода и паузы не менее 10 минут/двойного TTL. Перед DELETE заново
  проверяются владение, проект, назначение, активный IP и отсутствие адреса в DNS.
  Сначала Agent убирает собственный старый адрес, затем выполняются Detach
  (targeted_to="0" по официальному cherrygo), GET-проверка отсоединения и DELETE.
  Для удалённого IP Cherry может вернуть 403: это само по себе не подтверждение
  освобождения. Дополнительно требуется отсутствие UUID в полном инвентаре проекта;
  неполный список или остающийся ресурс не позволяют отметить освобождение.
  Нельзя удалять management, активный, чужой или неизвестный ресурс.
- Квота проекта учитывается за скользящие сутки; внешние 429 соблюдают Retry-After.
  При остановке по квоте забракованные кандидаты освобождаются, история остаётся.
  Сброс квоты не означает новый пул IPv4. Свои месячные/числовые лимиты владельцем
  отклонены. Точный счёт Cherry не подменяется оценкой; неизвестный тариф отмечается.
- После успешного перехода финансовая политика остаётся включённой. Внутренний
  одноразовый режим кандидата исчерпывается. При аварийном ручном вмешательстве
  финансовая политика отключается, ресурсы сохраняются для безопасной сверки.
- Sponsorship/ad_tag, Telethon и другие проекты не изменяются.

Состояние сохраняется в PostgreSQL: Recovery, Job, FloatingIP и SystemSetting
paid-recovery:UUID. Общая блокировка PostgreSQL сериализует покупки/DNS/очистку.
В журнале — стадии и error_id; ключи, пароли и ответы с секретами не записываются.

## Включение на конкретной ноде

Нужно установленное и зарегистрированное приложение Agent. Дополнительная опция:
`agent/install.sh --with-config-reader --with-network-helper`.
На ноде root создаёт `/etc/autoip-agent/floating-policy.json` с правами 0600,
содержимым `{"enabled":true,"management":"MANAGEMENT_IPV4"}`. Перед первой
операцией создаётся `/var/lib/autoip-floating-pilot/active.json` (0600) с
`address` текущего IP и `resource_id` ресурса; каталог принадлежит root, режим 0700.
Неверная или отсутствующая локальная политика запрещает работу помощника.

В Commander:

```sh
docker compose exec -T commander python -m commander.manage paid-recovery probe AGENT_UUID
# Дождаться succeeded у полученного задания Agent.
docker compose exec -T commander python -m commander.manage paid-recovery enable AGENT_UUID --approved --probe-id PROBE_UUID
docker compose exec -T commander python -m commander.manage paid-recovery status AGENT_UUID
```

Отключение: `paid-recovery disable AGENT_UUID`. Пауза Agent из панели/бота также
останавливает продолжение операций. Без --approved и успешной свежей сетевой
проверки включение запрещено. Настройки по умолчанию отключены.

## Что реально проверено

Покупка/Attach, добавление /32 и DNS ранее проходили отдельные согласованные
живые пилоты. Реальное переключение по подтверждённому инциденту на готовый
резерв завершилось успешно. Новый объединённый платный путь проверен тестами
с провайдерами, включая потерю ответа, повторы, квоту, историю и DNS-handoff.
На действующей ноде проверены ограниченный сокет и доставка задания через Agent.
В первом живом платном цикле после подтверждения в боте автоматически выполнены
покупка, Attach, настройка Linux, MTProto-проверки и DNS-переход. Очистка старого
ресурса потребовала исправлений: собственный снимок на момент очистки вместо
старого Telemt-снимка, отсутствие срока годности у уже выполненного задания,
Detach перед удалением и сверка инвентаря при 403 для удалённого IP. После
исправлений очистка завершена и освобождение сохранено в БД. Финансовый режим
остаётся включённым. Путь без ответа владельца (+15/+20/+25) проверен тестами;
этот живой цикл включал подтверждение в боте. Полный набор: 235 passed, 1 skipped.
