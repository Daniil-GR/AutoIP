# Согласованный DNS-тест с возвратом

Ограничение: только выбранный поддомен vetka.rest, только A-запись. Пилот
не включает платное восстановление и не заменяет проверку всего recovery worker.

## Как меняется запись

Используется REST v2 Dynadot: POST records с add_dns_to_current_setting=true
добавляет единственную новую A-запись; DELETE records передаёт только точную
старую A-запись в dns_sub_list. Снимок всей зоны никогда не отправляется на
перезапись. Пока присутствуют обе A-записи, оба адреса должны обслуживаться.
Проверяются сохранность других записей и TTL после каждого шага. Запрос подписан
по точным байтам JSON-тела, пути и request ID. Неизвестные форматы и неоднозначный
набор записей поддомена останавливают пилот до изменения.

Источник: https://www.dynadot.com/domain/api-document (SET_DNS, REMOVE_DNS).

## Локальная команда

```sh
python -m commander.manage dns-pilot prepare --operation-id UUID --agent-id AGENT_UUID --resource-id FLOATING_UUID --approved
python -m commander.manage dns-pilot switch --operation-id UUID
python -m commander.manage dns-pilot verify --operation-id UUID
python -m commander.manage dns-pilot restore --operation-id UUID
python -m commander.manage dns-pilot verify-return --operation-id UUID
python -m commander.manage dns-pilot status --operation-id UUID
```

Prepare требует отдельно согласованный тест и возврат, управляемый ready_standby
ресурс правильного агента и совпадение текущего DNS с конфигурацией. Сохраняет
снимок и исходное/новое значение в PostgreSQL. Switch не повторяется после
начала изменения. Перед каждым внешним шагом сохраняется checkpoint. PostgreSQL
advisory lock сериализует живые DNS-пилоты одной зоны, включая разные UUID.
Она не блокирует независимого оператора в панели провайдера; точечные запросы
исключают перезапись его других записей. При расхождении с исходным снимком
требуется разбор, а не восстановление старой зоны поверх чужих правок.

Restore сверяет исходный, новый или промежуточный набор двух адресов и выполняет
только необходимые точечные действия. При потерянном ответе не повторять Switch:
сверить состояние и использовать Restore. Статус в БД и аудит содержат operation_id;
неожиданные ошибки дополнительно получают error_id.

## Порядок живого теста

1. Проверить работу обоих IP и состояние ноды; сохранить резервную копию БД.
2. Prepare, затем независимый от интерактивного процесса таймер возврата DNS.
   Для текущего пилота используется systemd timer на Commander через 20 минут
   с повтором команды возврата при ошибке. Transient timer не переживает reboot;
   запись операции в БД переживает его. После перезапуска сверить незавершённые
   операции и выполнить согласованный возврат из журнала.
3. Switch; дождаться авторитетных NS и публичных резолверов. Успешный ответ API
   не означает, что авторитетные DNS уже обновились. Проверять MTProto по новому
   IP и домену; не считать один таймаут подтверждением блокировки.
4. Restore; подтвердить исходный адрес в API, на авторитетных NS и публичных
   резолверах, проверить доступность. После успешного возврата снять timer.
5. Сохранить результат. Оба IP остаются на ноде; управление, маршруты, ad_tag,
   Telemt и другие домены в этом тесте не меняются. При прямом HTTPS-тесте нужно
   фиксировать фактический адрес соединения; HTTP 200 не доказывает полный поток
   данных WEB-прокси. Нельзя выдавать неоднозначный ответ сервиса за успех MTProto.

Тарифные ограничения, DNS-кэши клиентов, доступность внешних проверяющих сервисов
и распространение настроек авторитетного провайдера ограничивают гарантии времени.

Готовность DNS в verify требует большинства выбранных авторитетных адресов
и большинства выбранных публичных резолверов. Ошибки и отсутствие ответа
не засчитываются как успех. Полное обновление авторитетных адресов отражается
отдельно в all_authorities_updated; dns_votes сохраняет числитель/знаменатель.
Для verified также обязательна реальная успешная MTProto-проверка по IP и домену.
Это не разрешение раннего удаления старого ресурса; пилот его не удаляет.
При неполной проверке CLI verify возвращает код 2, а не успешный код процесса.

Если выбранная запись уже возвращена, Restore выполняет только чтение и
сообщает other_records_changed при изменениях других записей. Это не ошибка
и не причина перезаписывать зону. После COMPLETED_RETURNED прежнее разрешение
пилота больше не позволяет менять DNS; допустимо только подтверждение уже
восстановленного адреса. Новое изменение требует нового согласованного пилота.
