# Состояние реализации и проверки

Проверено 28 октября 2026. Это рабочий этап разработки, а не заявление о готовности автоматического восстановления в production.

## Реализовано

- Изолированный Commander; FastAPI API сохранён, старые агенты могут передавать статус.
- Миграции Alembic v0.1 → v0.2, сохранение исходных данных, отдельная команда принятия старой БД.
- Вход по сессии HttpOnly/SameSite, CSRF, ограничение попыток входа, опциональная TOTP; Basic совместимость отключается при TOTP.
- Шифрование интеграций Fernet с отдельным мастер-ключом, привязка шифротекста к ID и типу интеграции, скрытый локальный ввод и защищённая форма. API не возвращает секреты.
- Подключение агента одноразовым кодом, опрос подключения, сохранение индивидуальных настроек и общих привязок интеграций, список недостающих условий.
- Автообнаружение Telemt, интерфейсов и маршрутов. Необязательный Unix socket broker с проверкой UID читает только разрешённые поля TOML. Polling Agent не получает root.
- Постоянный локальный журнал результатов заданий; TTL очереди, лимит повторов, отзыв доступа.
- Исправлен адаптер Check-Host по текущей документации: `nodes`, `location`, TCP dict results; RU и другие страны, ASN, IP отдельно от домена. Таймаут остаётся UNKNOWN.
- Реестр провайдеров мониторинга, отдельный worker, очередь проверок и таймеры инцидентов в PostgreSQL.
- Ручные решения, финальная проверка, повторные проверки +15/+20/+25 минут; события с недостаточными подтверждениями требуют ручной проверки.
- Telegram-бот на aiogram 3, отдельный процесс, восемь разделов меню, права по User ID и только личные чаты, одноразовые кнопки с TTL и привязкой к пользователю. Все операции используют общие сервисы Commander.
- Постоянный журнал уведомлений и подтверждённых доставок. После сетевого сбоя доставка повторяется; при аварии между отправкой и фиксацией возможно повторное уведомление (Bot API не предоставляет idempotency key).
- Панель на русском с восемью разделами, формами, фильтром агентов и графиком реальных сохранённых проверок. Начальная база пустая; демонстрационные данные используются только браузерным тестом.
- Cherry inventory/getMe проверки только чтением; локальный план DNS сохраняет остальные записи и запрещает автоматическое применение небезопасной записи зоны.
- Отдельный статус записи ad_tag: сохранение файла НЕ считается подтверждённым hot reload.
- Docker Compose с раздельными миграциями, API, worker, необязательным bot; loopback-only порт 18080, отдельные сеть/тома. Скрипты backup/restore только своего Compose проекта.

## Наблюдаемые проверки

- Исходный проект: 3 теста проходили до изменений.
- Новый набор: 52 теста прошли; дополнительный PostgreSQL тест запускается на отдельной пустой БД.
- Резервная копия действующей изолированной БД AutoIP восстановлена в отдельную тестовую БД; проверены версия схемы и две зашифрованные интеграции.
- PostgreSQL 16 в одноразовом контейнере: миграция с заполненной таблицей v0.1, повторная миграция и конкурентное устранение дублей проверок прошли.
- Настоящий Chromium: вход, восемь разделов, сохранение глобальных/индивидуальных настроек, форма ключей, desktop/mobile, отсутствие ошибок JavaScript и горизонтального переполнения.
- Реальные GET getMe и Cherry inventory прошли. Публичные DNS, сеть, платные IP и MTProxybot не изменялись. Результат getMe не проверяет доставку сообщений.

## Ещё НЕ готово для эксплуатации

- Не подтверждена независимая реальная работоспособность MTProto из РФ; второй источник не предоставлен.
- RIPE Atlas SNI: реализованы ручной запуск с подтверждением расхода кредитов, постоянный submit-once checkpoint и раздельные диагностические результаты. Новые реальные измерения не запускались; кредиты не расходовались. Проверка сертификата не подтверждает всю цепочку доверия и не является MTProto проверкой.
- Telethon: реализованы скрытая локальная авторизация, шифрование StringSession, сериализация диалогов аккаунта, консервативный адаптер регистрации/выбора канала, остановка на неизвестном ответе и очередь ad_tag. Сценарии проверены с подставным диалогом; реальный MTProxybot пилот не проводился.
- Нет согласованного сетевого пилота на новом Cherry Agent и проверенного аварийного отката маршрутизации.
- Не выполняется платный цикл создания/назначения/удаления Floating IP. Предпроверка восстановления сохраняет MANUAL_REQUIRED и причину, не имитирует успех.
- Нет безопасного автоматического DNS-переключения Dynadot: документация v2 описывает запись зоны без проверенного CAS. Не вызываем её автоматически.
- Авторизация Telethon выполнена; живой пилот диалога MTProxybot и hot reload конкретной версии Telemt ещё не подтверждены.
- Глобальные и индивидуальные лимиты сохраняются, но финансовое резервирование ещё не проверено реальными покупками. Учёт стоимости не является реальным счётом провайдера.
- HTTPS Commander опубликован через отдельный vhost; TOTP ещё не настроена. Backend остаётся на localhost:18080. Бот принимает команды только разрешённого User ID. Рабочие конфигурации v3a.tech не изменялись.

## Публикация панели и подключение первого VPS — 29 октября 2026

- Панель admin.vetka.rest опубликована с Let’s Encrypt; продление настроено через webroot и проверку Nginx перед reload. Существующие сайты продолжают отвечать.
- На новом литовском VPS установлен непривилегированный AutoIP Agent с исходящим HTTPS. Обнаружен Telemt 3.5.14, порт 9443 и SNI lt.vetka.rest. Сбор фактов больше не падает, если родительский каталог Telemt недоступен агенту; для чтения используется ограниченный локальный helper. Процесс и конфигурация Telemt при подключении AutoIP не менялись.
- Исходный IPv4 хранится отдельно как proxy_ip, не как Floating IP. Его можно использовать для проверок, в том числе когда он совпадает с Management IP. При появлении Floating IP мониторинг предпочитает его. Исходный IP не импортируется как управляемый платный ресурс.
- RIPE Atlas выбирает публичные IPv4-зонды по ASN Мегафон (31133), Билайн (3216), МТС (8359), Ростелеком (12389) около Москвы, Петербурга, Красноярска и Хабаровска (радиус 75 км). Координаты приблизительные, ASN не гарантирует мобильный доступ. Отсутствующие комбинации отображаются явно.
- Зарубежный контроль: Германия, Нидерланды, Финляндия, до трёх различных ASN на страну. Измеряется один IPv4 и фактический порт прокси с заданным SNI. Один таймаут и недостаточное покрытие не подтверждают блокировку. Сравнение остаётся отдельной диагностикой TLS, без доказательства MTProto или блокировки именно IP.
- План зондов доступен без API-ключа и не расходует кредиты. Список выбранных зондов, IP, порт и measurement ID сохраняются с задачей; неоднозначный POST не повторяется. Реальные измерения требуют сохранения отдельного RIPE Atlas ключа в панели и подтверждения кредитов. Чужие ключи существующих проектов не используются.
- В боте доступно подтверждение SNI-проверки через ту же логику Commander, а также кнопка веб-панели. Главное меню реально доставлено администратору.
- Платный цикл Floating IP, безопасная автоматическая запись DNS и сетевой откат остаются незавершёнными. Покупки, освобождение IP и автоматическое восстановление не включены. Отсутствие Floating IP сейчас не маскируется фиктивной покупкой.

Проверки этого этапа: 86 локальных тестов прошли (отдельный PostgreSQL тест пропущен без тестовой БД); Ruff, Python compilation и JavaScript syntax прошли. Реальный Chromium проверил HTTPS-вход, карточку подключённого агента и живой список зондов RIPE Atlas на desktop/mobile. Check-Host выполнил реальные проверки исходного IP и домена на порту 9443: сохранён результат reachable (только TCP). Тест продления сертификата Let’s Encrypt с deploy hook прошёл; существующие сайты проверены после reload. Тест TOTP сделан независимым от случайного перехода между 30-секундными интервалами, без изменения проверки TOTP в production.

После успешной живой TCP-проверки включён обычный Check-Host мониторинг с интервалом 180 секунд. Агент работает в ручном режиме; платные действия и запись DNS остаются отключены. RIPE Atlas не запускается планово без ключа и подтверждения кредитов.


## Два основных источника и раздельные протоколы — 29 октября 2026

По уточнению владельца обычный интервал изменён на 300 секунд в БД, настройках, Compose и примерах. Основные источники — Check-Host и MTProto Checker; RIPE Atlas теперь дополнительный источник, а не основной.

- MTProto Checker выполняет только MTProto-проверку на фактическом порту агента, с секретом выбранного MTProto-профиля. Поддерживаются dd (obf2) и ee (fake-TLS). Ключ передаётся только X-API-Key, секрет — только в POST JSON; query-ключи, полный ответ провайдера и секретные ссылки не сохраняются в журнале проверок.
- Литовский профиль использует dd и порт 9443. Веб-адрес lt.vetka.rest:443 проверяется отдельно через HTTPS Check-Host. Успех веб-страницы не считается проверкой передачи данных веб-прокси и не может скрыть отказ MTProto.
- DATA_CUT и RKN_BLOCK сохраняются как подозрение на недоступность MTProto из отдельной RU-точки при рабочей внешней точке. MT_DEAD/DOWN — деградация или недоступность сервиса, без вывода о цензуре; повторяющиеся уведомления подавляются до смены состояния. Открытый TCP не скрывает отказ данных MTProto. Одна точка MTProto Checker не выдаётся за все российские сети и мобильных операторов.
- Проверяются цель, порт, тип секрета, время и согласованность полей результата. Неизвестные, устаревшие и противоречивые ответы остаются неопределёнными. API-ошибка не превращается в блокировку прокси.
- Общий счётчик запросов на ключ сохраняется в PostgreSQL и блокируется между worker-процессами. Автоматика использует максимум 25 запросов в минуту из доступных 30, оставляя запас для ручных запросов. Retry-After и отказ ключа создают сохраняемый cooldown; автоматических повторов POST внутри запроса нет.
- Резерв RIPE Atlas срабатывает только при ошибке или неопределённом ответе основного источника, при разрешённом расходе кредитов и выбранной интеграции у агента. Не чаще раза в час на агента; пауза и отзыв агента запрещают автоматический резерв. Без ключа измерение не создаётся. Положительный TLS-результат не заменяет проверку MTProto.
- Панель и бот показывают MTProto и веб-HTTPS отдельно; выбор интеграций и формат секрета сохраняются в настройках агента. API-ключ Checker и существующий секрет литовского прокси импортированы зашифрованно; процесс и конфигурация Telemt не менялись.

Живые проверки: API-ключ принят, лимит 30/min подтверждён. Проверки dd/obf2 на 9443 вернули OK с успешными handshake/data из RU и внешней точки. Проверен также fake-TLS. Первый полноценный рабочий цикл сохранил Check-Host TCP для IP/домена, MTProto Checker OK и отдельный HTTPS-результат для веб-адреса; резерв Atlas остался standby. Ключ RIPE Atlas отсутствует, кредиты не расходовались. Платные IP и DNS не изменялись.

Проверки дополнения: 111 локальных тестов прошли; отдельно прошёл PostgreSQL тест миграции и конкурентных запросов, включая 40 параллельных попыток взять слот общего ключа (разрешено ровно 25). Ruff, Python compilation, JavaScript syntax, изолированный Chromium и живой HTTPS desktop/mobile прошли. Отдельный статус tcp_only показывает доступность TCP без подтверждения данных MTProto. Дополнительный SNI-результат не откладывает плановые проверки основных источников.
