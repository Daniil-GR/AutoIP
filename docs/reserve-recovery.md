# Подготовленное восстановление через существующий резерв

Режим `tested_reserve_only` обслуживает первый переход на уже купленный,
подключённый и проверенный Floating IP. Не покупает, не освобождает ресурсы,
не меняет сеть Linux, management IP, Telemt, ad_tag и Telegram-регистрации.
Не включает финансовый цикл последующих замен.

## Подготовка и отдельное включение

Из каталога Commander, только для согласованного агента:

```sh
docker compose run --rm --no-deps -T commander python -m commander.manage reserve-recovery prepare AGENT_UUID --resource-id FLOATING_UUID
docker compose run --rm --no-deps -T commander python -m commander.manage reserve-recovery status AGENT_UUID
```

Prepare сохраняет режим **выключенным**. Требуется завершённый реальный DNS-пилот
с возвратом именно для этого агента/доменa/резерва и совпадающего исходного IP.
Проверяются владение, история блокировок, факт присутствия обоих IP на интерфейсах,
активность Telemt, свежий heartbeat, интеграции и область DNS. Обязательного
фиксированного месячного бюджета для этого режима нет: новых заказов он не делает.

Только после отдельного разрешения владельца на будущие живые DNS-переключения:

```sh
docker compose run --rm --no-deps -T commander python -m commander.manage reserve-recovery enable AGENT_UUID --approved
```

Флаг --approved не заменяет согласование владельца. Обратное выключение:

```sh
docker compose run --rm --no-deps -T commander python -m commander.manage reserve-recovery disable AGENT_UUID
```

При выключении или изменении условий во время незавершённых DNS-операций worker
пытается вернуть исходную запись. Если её безопасный возврат не подтверждён,
останавливается с уведомлением; оба IP и ресурсы остаются на месте.

## Когда создаётся операция

Мониторинг работает раз в пять минут. Подтверждение в боте требует заключительной
проверки; без ответа сохраняются проверки +15/+20/+25 минут от уведомления.
Для автоматического пути нужны три последовательные проверки с независимыми
подтверждениями. Один таймаут, один источник или потеря heartbeat не запускают
смену адреса. Сравниваются отказы именно проверяемого IP; отказы только домена
не выдаются за независимое доказательство блокировки IPv4.

`recovery_plan` и бот используют ту же логику Commander. На агента допускается
одна активная операция. Ключ incident:UUID исключает повторное создание при
повторном подтверждении. Результаты устаревших проверок не открывают новый
инцидент во время уже выполняющегося восстановления.

## Этапы и сохранность

- FINAL_CHECK: повторная независимая проверка старого IP. Если он доступен,
  отмена; если данных недостаточно — ручная проверка.
- CANDIDATE_CHECK: GET Cherry подтверждает, что резерв назначен нужному серверу.
  MTProto из РФ/внешней точки должен пройти. Получается свежий снимок зоны.
- DNS_ADD / DNS_REMOVE: только точечные append/remove одного A-адреса поддомена.
  Перед каждым запросом сохранён checkpoint, повторно проверены назначение IP
  и разрешение. Зона целиком не перезаписывается. После потерянного ответа
  выполняется сверка чтением; второй запрос записи вслепую не отправляется.
- DNS_VERIFY: большинство выбранных авторитетных адресов и публичных резолверов
  должно выдавать новый IP; дополнительно обязательны MTProto по новому IPv4
  и по домену. Не ждём 100% мировых точек. Неопределённый ответ — повтор через
  30 секунд, а не успех, не новая покупка.
- COMMIT: DNS и назначение IP повторно сверяются. В одной транзакции обновляются
  активный Floating IP агента, ресурс, инцидент, история и уведомление. Устаревшие
  после перезапуска проверки требуют обновления. Режим автоматически выключается:
  резерв использован, дальнейшие покупки не разрешены этим режимом.

История подтверждённого старого IPv4 сохраняется после закрытия инцидента.
Основной адрес не удаляется. Если исходным был управляемый платный Floating IP,
он остаётся оплачиваемым; очистка требует отдельно подготовленного сценария.

Состояние — Recovery плюс SystemSetting recovery:UUID; разрешение — auto-reserve:AGENT_UUID.
JSON обновляется с фиксацией транзакции. PostgreSQL advisory lock общий с DNS-пилотом
сериализует внешние операции. Перезапуск worker продолжает с сохранённого этапа.
Изменения чужих записей во время мутации вызывают остановку/сверку без перезаписи.
При ошибках доступны error_id, agent_id, operation_id и этап, без секретов.

На 30-й минуте незавершённая операция уведомляет и останавливается для проверки,
сохраняя оба IP и текущее DNS. Один лишь истёкший таймер не откатывает потенциально
работающий новый адрес. Отдельный откат после изменения разрешения ограничен
10 минутами; затем ручное вмешательство и сохранение обоих адресов.

При аварии между сохранением маркера запроса и фактической отправкой запрос может
остаться неотправленным. Безопасное поведение — сверка и ручная проверка, а не
повтор потенциально неоднозначной записи. Это осознанное ограничение без CAS API.

## Что проверено

Интегрированный worker проверяется на изолированной БД и подставных ответах
провайдеров, включая потерю ответа и отказ финальной транзакции. Реальные детали
покупки, Attach, настройки /32, DNS-перехода и возврата проверены предыдущими
согласованными пилотами. Интегрированный автоматический запуск по настоящей
блокировке ещё не проводился. Само добавление кода и подготовка режима его
не включают и не доказывают работу во всех сетях РФ.

Telemt может сообщать public_host как исходный IPv4, тогда как клиенты используют
отдельно настроенный домен. Такое сочетание допустимо при успешном DNS-пилоте.
Worker фиксирует оба значения отдельно; изменение public_host после начала
операции останавливает её. Сам файл конфигурации Telemt не редактируется.

## Ручное подтверждение и частичная блокировка

После подтверждения администратором свежий нормализованный RKN_BLOCK или
DATA_CUT для текущего IPv4 при успешных TCP, хендшейке и данных внешней
MTProto-точки позволяет выполнить переход на подготовленный резерв. Требовать
одновременно отказа TCP во всех российских сетях в этом случае нельзя:
блокировка может затрагивать протокол или отдельного оператора.
Финальная проверка повторяет это условие непосредственно перед переходом.
Неопределённый, устаревший ответ, другая цель или отказ внешней точки не подходят.
Для запуска без ответа администратора сохраняются независимые подтверждения
и последовательные проверки +15/+20/+25 минут.

При DNS_VERIFY проверки IP и домена выполняются последовательно. Только
противоречивый ответ сервиса (inconsistent_response) повторяется один раз с
паузой; достоверный RKN_BLOCK/DATA_CUT и ограничение частоты не маскируются
повтором. Каждая попытка учитывается в общей квоте ключа. Для успешного
завершения по-прежнему необходимы обе полноценные MTProto-проверки.
