# Поддомены WEB-прокси через бота

В меню бота: **Поддомены CDN → нода → новое имя → Создать и настроить**.
Допустимы только свободные одноуровневые имена `*.vetka.rest`, без wildcard,
служебных имён и делегированных вложенных зон. Секреты бот не запрашивает.

Мастер добавляет имя к существующему Gcore-ресурсу; платные ресурсы не создаёт.
Проверяет лимит аккаунта, свободный DNS, Forward Host и отсутствие origin Host
override, закреплённый SSH-доступ и совместимость действующей конфигурации.
Добавляет ровно одну CNAME-запись Dynadot через append API с проверкой сохранности
остальной зоны. Список дополнительных имён Gcore сохраняется и сверяется перед
обновлением; при конкурирующем изменении выполнение останавливается.

Добавление домена к ресурсу с Let's Encrypt вызывает перевыпуск сертификата
Gcore для актуальных имён. Мастер не создаёт новые объекты сертификатов, не
вызывает force-retry и не отключает старый HTTPS. Ожидает подтверждённый CNAME
и доверенный TLS нового имени. Из-за лимитов CA не добавляйте много имён подряд:
групповое добавление имён в одном перевыпуске пока не реализовано.

После этого выполняется закреплённая копия помощника TelemtProxy из коммита
`202aedd1a531435ed7fdf0686f8e430571684712`, SHA256
`81c9d5d50d0fefea6e6f113d4624a3b955114644bbdd147b40f80307c65fe752`.
Помощник сохраняет закрытые резервные копии, проверяет Nginx, перезапускает Telemt,
проверяет локальный сайт, перезагружает Nginx. При ошибке изменения файлов
откатываются. Возможен краткий перерыв всех подключений этой ноды.

Последняя проверка выводит на VPS доменную capability из существующего секрета
и проверяет выдачу авторизованного bridge через CDN. Секрет/capability/HTML не
передаются в сообщения, БД или журнал Commander. Итог **Готово к проверке**
означает проверенные DNS, TLS и bridge. Передачу данных в реальном Telegram
из конкретной РФ-сети администратор проверяет отдельно.

Каждый этап, согласие и ошибка сохраняются в PostgreSQL (`ControlTask`, `Audit`,
`Notification`). После перезапуска worker продолжает незаконченный этап. Записи
DNS и CDN получают checkpoint *до* отправки. При неоднозначном ответе повторная
запись не выполняется: сначала сверка фактического состояния. Кнопка «Повторить
сверку» возвращает операцию на тот же этап. При часовом тайм-ауте выдаётся
уведомление. «Остановить» сохраняет уже добавленные настройки; автоматическое
удаление DNS/CDN намеренно отсутствует, чтобы не задеть действующие имена и
сертификат. Неудача на VPS требует проверки его закрытого журнала отката.

## Привязка ноды

Один раз локально на Commander, из venv с asyncssh:

```sh
.venv/bin/python scripts/bind-cdn.py AGENT_ID \
  --ipv4 MANAGEMENT_IP --source-host proxy.vetka.rest \
  --resource-id RESOURCE_ID --cname cl-EXAMPLE.gcdn.co \
  --gcore-id GCORE_INTEGRATION_ID --dns-id DYNADOT_INTEGRATION_ID \
  --ssh-key-file /secure/agent-key --known-hosts /root/.ssh/known_hosts
```

Нужен ранее проверенный SSH host key; автоматического TOFU нет. Существующий
закрытый ключ импортируется в зашифрованную интеграцию `cdn_access`, не
монтируется в контейнер и не выводится в терминал. Скрипт проверяет соответствие
Management IP агенту и не заменяет уже существующую привязку. Сама привязка не
создаёт домен, не меняет конфигурацию ноды и не разрешает финансовые действия.

Полный новый цикл на реальном поддомене требует отдельного подтверждения в боте.
Проверки с моками не являются проверкой реальной записи CNAME/перевыпуска TLS.
