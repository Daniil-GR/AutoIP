# Спонсорство Telemt

Floating IP не требуется для первой регистрации: Commander использует текущий
адрес прокси (`floating_ip`, если он задан, иначе `proxy_ip`) и MTProto-порт агента.
Основной Management IP при этом не меняется. Адрес WEB-входа и MTProto-порт
не следует путать: успешный HTTPS-ответ не подтверждает ни передачу MTProto,
ни показ спонсорского канала.

## Порядок пилота

1. Сохранить отдельную авторизованную интеграцию Telethon, MTProto-secret и
   публичный спонсорский канал в настройках агента.
2. Проверить существующие регистрации в MTProxybot, чтобы избежать дубликата.
   Пустая история AutoIP сама по себе не доказывает отсутствие регистрации в боте.
3. Получить отдельное подтверждение оператора на реальный диалог MTProxybot и
   изменение `general.ad_tag` действующего Telemt. Установка агента сама по себе
   не разрешает запись конфигурации: нужны оба разрешения защищённого helper.
4. После подтверждения зарегистрировать текущий IPv4:MTProto-порт с существующим
   базовым secret, получить ad_tag и назначить канал. Неизвестные ответы бота
   останавливают сценарий; повторная регистрация при неопределённом результате
   запрещена до ручной сверки.
5. Agent сохраняет резервную копию и атомарно меняет только `general.ad_tag`.
   Персональные теги `access.user_ad_tags` имеют приоритет и требуют отдельной
   проверки. Смена IP или порта во время диалога запрещает применение результата.
6. Проверить фактический hot reload и новые соединения. Успешная запись файла
   пока означает `TAG_WRITTEN_UNVERIFIED`, а не подтверждённый показ канала.
7. Проверить канал в целевом Telegram-клиенте отдельно для обычного MTProto и WEB.
   WEB Telemt передаёт логические MTProxy-потоки через общий relay; это не
   универсальный HTTP-прокси для произвольного браузерного трафика.

Адаптер MTProxybot реализован и проверен с подставным диалогом. Актуальные
сообщения/кнопки реального бота и сквозной показ канала должны быть подтверждены
живым пилотом. Ошибка спонсорства не останавливает прокси.
